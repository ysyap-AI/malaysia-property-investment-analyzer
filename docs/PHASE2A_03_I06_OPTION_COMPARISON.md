# MPIA — I06 security options and runtime comparison

20 October 2026, Asia/Kuala_Lumpur. Design only; no option selected by the owner or implemented. Read with the [preflight report](PHASE2A_03_I06_SECURITY_PREFLIGHT_REPORT.md) and [decision/approval matrix](PHASE2A_03_I06_DECISION_APPROVAL_MATRIX.md).

**Prefer D for the production database operation boundary and isolated Node for both reference qualification and provisional deployment.** A is technically plausible as a reduced-grant trusted-server writer, but does not give the database an enforceable full-operation boundary. D is a new execution design requiring explicit SQL-interface approval and v1 parity evidence. Its shared trusted gateway still can impersonate an actor if compromised; stronger independent human authentication is unresolved for both proposals.

Evidence: F = locally inspected source/configuration; H = historical execution; V = official documentation/versioned upstream source; P = proposed inference/design; U = unverified experiment. Feasible does not mean qualified, authorized, installed or deployed.

## 1. A versus D

| Dimension | A: dedicated raw SQL login/execution identity | D: execute-only caller + restricted SECURITY DEFINER capability |
| --- | --- | --- |
| Database-enforced boundary | P: deny unrelated tables/columns, ownership/DDL/admin, history rewrite and provider writes through exact grants/RLS. Raw H INSERT and S pointer UPDATE remain available | P: caller denied raw P/H/S/R DML. Only reviewed function signatures reach narrow owner rights. Function validates complete operation before modifying rows |
| Six requested guarantees | Finance/old-history protection can be designed; owner request checks rely on intact gateway; full CAS/actor protocol cannot be guaranteed by current raw grants/guards | Stronger enforcement of sequencing/CAS/replay/append, conditional on correct body. Actor UUID from trusted gateway remains an assertion, not independently verified human identity |
| Actual I05 SQL change | Must remove/replace literal SET LOCAL service_role; add fixed new-role/context setup and RLS policy integration. Preserve algorithm and v1 | Existing sequence cannot be used as-is. New private executor calls capability inside outer transaction. Keep accepted core unchanged as parity reference; explicitly approve replacement execution model |
| Additive migrations | New roles/ACLs and SELECT/INSERT/UPDATE policies; P lock-only policy design; no rewrite of accepted migrations | New trusted schema/function signatures/EXECUTE ACL, nonlogin owner/caller provisioning, narrow owner data rights and matching RLS. Existing tables/guards remain intact |
| Parent-first locking | Retain core P FOR UPDATE before S. Invoker pointer guard independently locks P; caller must have P lock privilege | Capability acquires P then S. Its owner satisfies both P lock sites. Caller cannot lock/read P directly. No hidden trigger elevation or omitted lock |
| Minimal P UPDATE privilege | Required at least one column. Candidate owner-scoped UPDATE USING plus false WITH CHECK could allow locks but deny actual updates; untested | Required on nonlogin owner, hidden from caller. Owner still not table owner/BYPASSRLS. Function never performs a Phase 1 UPDATE |
| CAS/idempotency | Existing core does it; stolen raw identity may omit WHERE expectation or append outside protocol. Guard checks newest same-property row, not complete admission | Function must enforce original expected tokens, contiguous next version, duplicate-before-new-state checks, owner/input-before-duplicate checks, exactly one pointer CAS and no old-pin replay |
| Trusted actor | Fixed-project verifier sets request-private actor; any SQL claim GUC is forgeable by that shared SQL identity | Fixed-project verifier feeds private capability call; function locks P and compares owner. Arbitrary authorized caller can forge an actor argument unless an independent attestation mechanism is added |
| Forged browser input | Closed intent builder, no actor selector, verified bearer, locked owner/input, RLS | Same admission requirements. SQL function also rejects malformed fields, prohibited operations and protocol shortcuts. No generic JSON-to-table writer |
| COMMIT certainty | Existing explicit outer transaction/port contract preserved after setup change; real adapter evidence needed | Same explicit outer COMMIT required. Function return is provisional; no internal COMMIT. PostgreSQL rejection/ROLLBACK tag and transport UNKNOWN distinctions remain |
| Unknown outcome/reconciliation | Same-ID retry can create or return original version. Changed input/owner/deletion can block retry; separate authorized historical reader needed | Same limitation must be preserved, not silently bypassed inside function. Optional separate read capability requires current-owner authorization and cannot republish |
| V1 serialization | One existing TypeScript implementation retained; lower parity burden | Largest new design burden: locked-row fingerprint and command preimage must match existing ECMAScript bytes, binary64 and lexical receipts. JSONB reserialization is unacceptable without proof |
| Operational complexity | Lower application change; higher reliance on raw-writer discipline and complete role/RLS review | Higher SQL review, owner/function lifecycle, schema migration and parity maintenance; narrower runtime execution surface |
| Compromise radius | Location raw writes across forged actor contexts possible; finance denial conditional on exact grant/indirect-path audit | Restricted to function effects, but may still span users through forged gateway actor. No raw financial writes; function defects and owner escalation paths are critical |
| Tests | Exact privilege/RLS lock tests, raw abuse demonstration, actor-GUC forgery, all existing protocol plus real driver cases | Raw table/owner SET denial, capability bypass attempts, actor trust residual, byte/semantic differential tests, all real locking/CAS/commit/driver tests |
| Maintainability | Fewer duplicate rules, but each caller must obey protocol; new grants/functions can enlarge authority silently | Central operation contract, but SQL and TypeScript oracle can drift. Version interface, review every overload/owner/ACL change, maintain differential vectors |
| Existing inspected support | F/H: current raw core, accepted guards and synthetic local service-role transaction tests. New-role success unproved | V: PostgreSQL definer mechanism. F: no such capability exists. Function-specific concurrency/security/parity evidence entirely absent |
| Disposition | Alternative only with explicit residual-risk acceptance and separate setup/grant design | **Conditional production design recommendation**, not ready for SQL coding/connectivity |

The lock-only policy possibility uses the PostgreSQL policy distinction between UPDATE USING, applied to a locking SELECT, and WITH CHECK, applied to actual new row values. It needs an applicable SELECT policy, one permissive UPDATE USING path and no competing permissive policy that permits an actual update. Do not infer it from today's authenticated policy or adopt authenticated membership. [PostgreSQL policy rules](https://www.postgresql.org/docs/17/sql-createpolicy.html).

D's nonlogin owner must have only the necessary P column read/lock, H read/append, S read/insert-pointer update, R eligibility and spatial/helper rights. Caller cannot SET owner, create in trusted schemas, replace the function or exploit PUBLIC/alternate overloads. The exact matrix is in report section 3. Neither design is protected from a trusted migration administrator intentionally changing it.

## 2. Alternatives and bridges

| Alternative | Disposition |
| --- | --- |
| B: dedicated NOINHERIT login allowed SET service_role | Synthetic bridge only if separately authorized. Preserves I05 SQL but permits broad effective service privileges, including financial tables. Never evidence that A/D least privilege has passed |
| postgres/admin bootstrap then SET LOCAL service_role | Rejected runtime model. Session authority can recover broader rights; historical postgres was nonsuperuser but still BYPASSRLS/CREATEROLE/CREATEDB with broad membership/ownership |
| SECURITY INVOKER wrapper | Does not remove caller's raw data rights. Useful code organization, insufficient security boundary |
| Separate REST table requests | No reserved multi-statement SQL transaction. Rejected authoritative writer |
| Single PostgREST definer RPC | Possible D variant, but outer HTTP transaction/COMMIT and identity/provenance semantics differ from current port. Direct SQL is the reference so exact tags and cleanup can be qualified. Public user RPC requires separate transport/command-authority design |
| Postgres.js, ORM, serverless HTTP SQL | No demonstrated superiority for exact completion/disposal protocol. Additional wrappers/automatic transactions/retries obscure evidence. Reconsider only if selected reference fails and a new reviewed candidate offers a concrete advantage |

Vendor support for the comparison:

- pg transactions require one client; pool destroy-release disconnects rather than reuses it. These APIs do not establish bounded physical cleanup on MPIA's target. [Transactions](https://node-postgres.com/features/transactions), [pool API](https://node-postgres.com/apis/pool).
- pg rowCount can be null for commands without counts; result.command is separate. Custom timestamp parsing avoids JavaScript Date's microsecond loss. [Result API](https://node-postgres.com/apis/result), [type conversion](https://node-postgres.com/features/types).
- Hyperdrive documents transaction affinity/reset, a minimum five origin connections and soft maximum sizing. Those properties constrain the budget; no hard global cap is inferred. [Connection pooling](https://developers.cloudflare.com/hyperdrive/concepts/connection-pooling/).
- Use a cache-disabled binding for all writer authorization/reconciliation work; origin verify-full adds hostname verification. Binding creation itself attempts database connectivity and requires separate connection approval. [Caching controls](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/), [TLS identity](https://developers.cloudflare.com/hyperdrive/configuration/tls-ssl-certificates-for-hyperdrive/).
- Supabase documents Edge DB URL, secret-key dictionaries and legacy service-role keys as defaults. Actual project injection scope is uninspected; stronger credentials must be demonstrably absent or the wider compromise radius explicitly accepted. [Edge environment](https://supabase.com/docs/guides/functions/secrets).
- Deno exposes client/query/pool APIs and configurable result decoders. Supabase's database integration example establishes a pattern, not qualification of @db/postgres or a credential ceiling. [Deno PostgreSQL API](https://jsr.io/@db/postgres/doc), [Edge database integration](https://supabase.com/docs/guides/functions/connect-to-postgres).

The dedicated isolated Node service is the clearly preferable compatible alternative to embedding a writer in the current Lovable server. No need to select another framework, managed product, ORM or public endpoint during this preflight.

## 5. Exact reference candidate and deployment recommendation

P: reference environment is **a separate private Node v24.18.0 harness, pure JavaScript `pg@8.16.3`, one standalone Client per attempt with a bounded harness-level concurrency limit, direct TLS connection to an explicitly authorized synthetic target**. It receives only the selected restricted identity, public Auth config and fixed manifest. It imports existing canonical/contracts modules; no admin client, browser client, provider integration or existing database runner. Direct/session pooler fallback is not automatic. Node version is locally present, not a support/security certification.

The exact pg version is a reproducible candidate, not a latest-version or security endorsement. Its official tagged package exists, supports ESM and declares ranges for dependencies including pg-pool/protocol/connection-string, so **pg pin alone does not pin the driver tree**. A future separate dependency approval must include exact resolved transitive versions, integrity/lock and security/support review. Cloudflare's current driver documentation lists pg 8.16.3 as the minimum supported Hyperdrive version; this is compatibility evidence only. [Tagged package](https://raw.githubusercontent.com/brianc/node-postgres/pg%408.16.3/packages/pg/package.json), [Cloudflare supported drivers](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/).

V: inspected pg@8.16.3 Client source shows query_timeout is a client callback timeout path, while end force-disconnects when a query is active. P: prefer quarantine and public end on the invocation-owned standalone Client rather than a late cancellation request against a recycled backend. Still test actual socket/session/lock disappearance and close acknowledgement within the cleanup budget; do not access private driver internals. Fail the candidate if the bounded cleanup contract cannot be met. [Versioned Client source](https://raw.githubusercontent.com/brianc/node-postgres/pg%408.16.3/packages/pg/lib/client.js).

P: **provisional production candidate is the same isolated Node/pg direct-TLS service**, using D's execute-only identity after D is implemented/qualified. The reference and deployment model deliberately do not differ in socket/pool semantics. The actual deployment provider, region, runtime patch and process/secret isolation are not selected or authorized. A production-like harness is a candidate, not evidence of deployed reliability.

A dedicated Worker/pg/Hyperdrive remains a plausible later deployment alternative if operations/cost requirements justify it. It would be a different qualification environment, even with the same pg version. It must prove origin-side in-flight cleanup and quarantine semantics, exact compatibility date/bundling, cache-off behavior, origin TLS and connection headroom. No “Node passed, therefore Worker passed” transfer. Deno Edge remains deferred until both stronger-secret reachability and physical-disposal blockers close; no assumed platform switch removes default admin credentials.

## 6. Adapter acceptance contract common to A/D

| Boundary | Required mapping / experiment |
| --- | --- |
| Query results | Only expected successful BEGIN/SET command-only results normalize to rows:[]/rowCount:0. SELECT and DML RETURNING must have exact safe counts matching rows; no blanket NaN/null coercion, fabricated counts or accepted multi-result ambiguity |
| Integer/float | int8 stays exact string/bigint until accepted safe bounds. Float8 coordinate binding/decoding preserves finite binary64; no decimal rounding or JSONB hash reconstruction |
| Timestamp | Per-client parser receives raw PostgreSQL timestamp text/OID 1184 before Date; validate finite supported calendar/range, normalize offset to UTC while preserving all six fractional digits. Include OID 1114 only with explicit semantics if encountered; reject unexpected type. Original receipt lexical bytes stay in command hash |
| Successful COMMIT | Return COMMITTED only for genuine completed COMMIT command. Aborted transaction completion ROLLBACK maps ROLLED_BACK. Known completed server rejection maps REJECTED only with qualified provenance/completion |
| Uncertain COMMIT | Throw, cancellation, network/process loss or missing/contradictory completion maps UNKNOWN; discard without rollback claim. No automatic reconnect/retry of a partial transaction |
| Reservation/cleanup | One invocation owns physical generation, not just wrapper object, from acquisition through cleanup. Synchronous quarantine before asynchronous close; late acquisition and release cannot free another borrow. Independent cleanup budget. Acknowledged commit survives release/log failure |
| Timeout layering | Current I05 proposals: auth/build 2s, acquire 2s, statement 5s, total transaction 8s, cleanup 1s; server lock3s/statement5s/idle10s. These are not a proved global wall-clock bound or host SLO. No Auth/provider I/O while locked; no silent deadline extension |
| Capacity | Initial reference concurrency cap 2 (one serial case or two-writer race), separate observer cap 1; operator must approve total target headroom. Production worst case includes all replicas, overlap/restarts, cancellations and operator reserve; apply DB role limit/admission control, not default pg pool size |
| TLS | Fixed endpoint/CA/hostname; negative wrong-CA/wrong-host/plaintext tests. Never disable validation to get a pass. A local socket/loopback exception would require explicitly approved isolated-test scope |
| Logs | Allowlisted diagnostics only. Sanitize Auth/driver/notice/pool/runtime/APM/DB/proxy sinks; do not wrap raw errors in existing SSR logger or log DSN/query/binds. Test private canaries in each sink |
| Target binding | Immutable manifest plus operator/control-plane project mapping; later read-only DB role/catalog/route probes and authorized wrong-project test. Matching database name/schema/user UUID is insufficient |

The reference should first investigate transport/lifecycle on a harmless private qualification harness only after explicit connection authorization. To exercise unchanged I05 end-to-end, B would require its own synthetic bridge risk approval; selecting D does not implicitly authorize B. To exercise D's actual effects, the reviewed capability must first exist on the authorized test target under separate migration/provisioning authority.

No driver or dependency was installed; no build changed; no Worker, Edge or Node endpoint started. All actual host/Auth/SQL qualifications remain NOT EXECUTED.
